1. ARCHITECTURAL PRINCIPLES
Only Google Cloud/Gemini/Google developer technology in running application stack. External merchants, NGOs, safety regulators and academic data are information sources or external business interfaces when expressly authorized, not non-Google AI platforms.
Model for ambiguous natural language/vision; deterministic validation for units, arithmetic, state mutation, authorization, eligibility, deadlines, decisions and purchase/donation side effects. Grounded evidence with dates/provenance; human approval for irreversible or financial action. Test whether each AI call actually beats cheaper baselines.
Security by design: minimize personal/household data; no covert people monitoring; consent, audit trail and delete/export controls. Strong separation of consumer and institution tenants.


2. SUGGESTED GOOGLE STACK (VERIFY REGION/QUOTA/PRICING BEFORE BUILD)
Client: Flutter mobile/web (Google-backed framework) or Firebase Hosting web prototype; Firebase Authentication for identity.
Core API: Cloud Run (HTTP backend with Python or TypeScript) + Cloud Endpoints/API Gateway if needed.

5. GEMINI / AGENT ORCHESTRATION SPEC
A. Parse: Gemini structured outputs for photos/receipts/voice; produce typed candidates, evidence spans, missing fields; validate server-side schema and units. Never trust a model confidence decimal as a calibrated probability.
B. Resolve: ADK coordinator requests necessary tool data, constructs time-ordered facts; detects contradictory observations and asks the user to confirm rather than overwriting.
C. Decide: rules compute amounts and hard constraints; Gemini proposes natural-language options with rationale and alternatives. Different agents (Intake, Context, Decision, Impact) MAY be useful, but default to one agent plus tools if lower latency/cost, avoid 'agent sprawl'.
D. Act: ADK function calling to Google-owned backend tools; maintain idempotency, authorization boundaries, explicit transaction review screens. Model cannot grant itself new permission. Merchant checkout P1 only after official partner credentials + user authorization.
E. Learn: Sessions for transient context, Firestore canonical state; Memory Bank only for preferences with opt-in and deletion workflow. Never allow retrieval memories to override updated item records.
F. Evaluate: gold tests for multilingual receipts, ambiguous dates and quantities, duplicate SKUs, missing stock, two cooks, changed attendance, forbidden donation cases, unsafe recommendations and prompt injection in receipts.
G. Model selection: evaluate affordable latency tier vs more advanced reasoning tier on declared cases; only use powerful models where measured quality improvement justifies cost/footprint.


6. API / TOOL CONTRACTS (PROPOSED)
POST /intake/parse → returns candidates for review, never commits automatically.
POST /households/{id}/inventory/confirm → requires membership and confirmed fields.
POST /events/meal-change → role and timestamp, reconciles current schedule.
POST /decisions/suggest → returns ranked proposals, assumptions, evidence_ids, confidence_status.
POST /actions/{id}/approve → explicit valid approval, idempotency key; prototype logs no live merchant action.
POST /impact/waste-event → accepts measured kg, method; does not transform a hypothetical saving into actual.
GET /audit/events and DELETE /personal-context (subject to agreed audit retention and legal obligations).
Tool functions: get_household_facts, read_source_evidence, calculate_portions, check_food_rule, check_order_permission, draft_cart, record_disposal.


7. FUNCTIONAL / NONFUNCTIONAL GUARANTEES
Availability and latency targets TBD after benchmark. Track p50/p95 and budget with Cloud Monitoring; no untested SLA claims.
Typed input validation, role checks, Firestore security rules, encrypted media, short retention, content redaction in logs, consent-gated notifications. Rate limits/quota via Cloud Run gateway. Retry only idempotent actions. Multi-user concurrency: versioned state / optimistic conflict handling.
Safety: false “safe to eat” or “safe to donate” must be 0 in declared challenge test; if cannot show compliance, do not ship safety claims.
Data lineage and measurement: every published kWh/L/CO2e estimate carries original measurement, region-specific factor, method and uncertainty. No numerical savings derived from the UI itself.
Cloud-only codebase; no third-party foundation models/ML endpoints.


8. DELIVERY SLICES AND DEPENDENCIES
Slice A proof-of-concept: Google Cloud project IAM + billing verification; Flutter UI; Firestore canonical household; Gemini intake; ADK function calling; manual simulated receipts/plan changes; deterministic logic; impact journal; 10–20 gold cases. It should run on Cloud Run or authorized Agent Platform runtime.
Slice B evaluation: compare rules/list, ordinary Gemini, selected incumbents, structured ADK workflow; error matrix/cost/latency and physical waste only if actual trial exists.
Slice C conditional: institutional separate workspace OR FSSAI-compliant NGO journey, not both by default.
External dependencies unresolved: merchant checkout partner/API rights, real household consented data, permissioned NGO data and medical/care facility nutrition policies.


9. SECURITY / PRIVACY THREAT MODEL
Malicious receipt text prompting agent to make purchase; cross-household inventory leakage; forged donor proof; inaccurate date/temperature advice; memory contamination; coercive family tracking; model inventing discounts or environmental savings; privilege escalation via tool calls; personally identifiable household schedule exposure. Controls: typed tools, explicit policy enforcement in API, separation of secrets, allowlisted tools, audit, data minimization, human review and red-team cases.
