ECOLOOP AI — CONSUMER EXPERIENCE & SCREEN MAP v0.3
15 October 2026 | Design exploration, NOT implemented. Scope is everyday consumers ONLY, optionally linked household. Corporate, NGO and waste-processing operator products OUT of this version. Canonical web stack: Next.js App Router, TypeScript Firebase App Hosting; FastAPI Cloud Run; Google ADK + Gemini; Firestore facts; optional approved commerce MCP. Whimsical editable onboarding and daily loops https://whimsical.com/9B1ywYtq7VHwQ8ZvAZ4MkE . Prior product master https://docs.google.com/document/d/1vUPWozAbRPcEhdLW0Bd9gAhhLKYXsY8Kn3s0t8wiKHA/edit .
1. CORE PRODUCT JOBS & POSITIONING
Product promise: EcoLoop helps someone use food already at home, plan meals, shop more intentionally, coordinate with people sharing a kitchen, and record outcomes with minimal effort. Climate/waste reduction an evidence-based possible result, not something auto-scored when AI replies. User can start SOLO and never join a family. Shared FAMILY can be created/joined later; no compulsory individual food diary or intrusive monitoring. Useful tasks: 'what do I have?', 'what should I cook or eat?', 'what should I buy?', 'what needs attention?', 'was food eaten/stored/shared/discarded?'. A generic chatbot and scanner have existing competitors, but a connected low-friction cycle is the hypothesis to test.
2. CORE USER STATES, MODES, PRIVACY
ACCOUNT: guest demo seeded data OR sign-in Firebase Auth Google/email. DEMO visibly tagged, never a real merchant connection. Profile options: SOLO household with only owner, CREATE family, JOIN family by invite code/link + permission. A single user may belong to multiple households later, NOT necessary P0. Roles: family owner/admin (invites, shared access), member (plans, shared items if permitted), limited cook/helper (meal/stock view with permission). No individual children's accounts needed P0.
FAMILY PRIVACY: share grocery inventory, household shopping list, count eating at a meal and meal-prep status. Personal spending/orders, reasons for eating out, health info, precise whereabouts, portion sizes eaten by individual remain PRIVATE unless a person deliberately shares a limited summary. A person can tell household 'not eating dinner' without sharing restaurant order. Household connection does not authorize reading someone else's merchant account. Family shared reminders assigned only where actor permits. Support revoke invite, remove member with explanation of effect on shared records, per-event actor and timestamps.
PERSONAL PREFERENCES optional: approximate meal windows or 'no schedule', cuisine, disliked ingredients, vegetarianity or dietary style, cuisine goals, household staples; avoid exact sensitive health facts unless explicitly consented and necessary, and do not provide diagnosis/medical treatment. Allergy handling flagged serious, user must confirm and never rely solely on Gemini for clinical/allergen safety.
3. ONBOARDING / FIRST VALUE — SCREEN FLOW
S01 Landing: branding 'Waste less food without more planning'; benefits use-soon, smarter shopping, adaptable meals; actions Sign in or Try demo; no inflated carbon counters.
S02 Login: Google or email authentication via Firebase; privacy link; demo without external account.
S03 Kitchen type: choice SOLO / CREATE FAMILY / JOIN FAMILY, default SOLO; explain family option can be added later. Solo account is still a one-member household for common data model.
S04 Create family: name household and choose optional shared role; invite later with link/email/code. Join family: enter code/open link, see household owner/name, request acceptance, accept shared data scope; no automatic household access.
S05 Light preferences (skippable): typical meal times optional; food preferences, 1-2 goals such as cook at home more or avoid duplication; choose only alerts useful to user. No full dietary intake questionnaire.
S06 First capture (skippable): enter 3–5 foods manually / take fridge photo / upload grocery receipt / photograph handwritten shopping list. Gemini candidate extraction; show kind of photo recognized; no pantry claim on unobserved item.
S07 Confirm candidates: list name, category, quantity/unit, user-confirmed date type and confidence, 'Not sure' possible, choose shared or private. Save only confirmed fields; image doesn't certify safety. Include clear 'Skip' and 'Edit'.
S08 First useful value: a meal/use-first/avoid-duplicate suggestion immediately if enough validated facts; if none, show 'what would you like to plan today?' and quick sample. Offer connection option LATER, never required for value.
S09 Home Today: core entry to everyday jobs, first personalized alert only when data supports it. Ask for browser push permission only after explicit intent to receive useful notifications, not at sign-in. Target first value under two minutes is a test TARGET not achieved metric.
4. HOME / TODAY INFORMATION HIERARCHY
Persistent browser navigation: Home, Kitchen, Ask, Shopping. Plans reachable by home card or contextual button; Family/Connections/Profile under top avatar. On narrow screens 4 bottom nav tabs; responsive desktop side navigation. Home content priority: (1) One high-value actionable card: 'check item due date', 'adjust tonight dinner', 'shopping essentials', or 'start planning'; (2) NEXT MEAL with people/attendee count only if opted in; (3) NEEDS ATTENTION grouped 'verified use-by', 'best-before', 'not checked recently' and 'low staple'; (4) Smart shortcuts: What can I cook?, Scan grocery, Update meal plan, Add item; (5) optional personal progress based actual recorded events. Empty home remains useful: start cooking chat or capture shopping list. Do NOT bombard with 10 daily red 'expires today' items when dates are unknown.
5. DAILY FLOW A — USE SOON REMINDER, COOK / SHARE / DISCARD
Trigger: user has VERIFIED package date or an item confirmed longer ago / explicit user-set use target. System schedules in-app reminder opt-in; push via Firebase Cloud Messaging on supported secure browsers/PWA and explicit permission, not mandatory. Distinguish (a) labeled use-by/expiry, (b) best-before (quality-oriented) and (c) estimated/unknown freshness. Never invent expiry for loose produce and never certify edibility by image/smell. Language for uncertain produce 'You last confirmed spinach 3 days ago—check before planning', not 'safe until tomorrow'.
Screen A1 Notification center / Home use-soon card: photo/item, source 'Label entered on 12 Oct', exact date type and last confirmed; 'Cook with this', 'Mark used', 'Share at home', 'Review/Discard', 'Snooze'.
Screen A2 Use-now cooking: recipe suggestion prioritizing items and preferences, estimated portions, missing ingredients highlighted. User confirms food is actually present/usable, especially time/temp-sensitive items.
Screen A3 Share: first-phase only share within household to another person to use, or tell family that ingredient is available. Community donation CTA is FUTURE verified-partner workflow, only for eligible safe surplus, not expired food, leftovers from plates, spoiled food.
Screen A4 Disposal decision: user chooses 'Used', 'Shared in home', 'Stored', 'Discarded', 'Not here/incorrect record'. For discard offer reason [spoiled, cooked too much, expired label, didn't like, other, unknown], optional measured amount or estimate explicitly marked; optional locally verified wet/dry disposal instruction, not unverified municipal partner or compost eligibility. No forced daily waste survey.
System: update canonical stock with actor and timestamp; only verified discarded edible grams count toward actual logged waste; if quantity unknown 'disposed unknown' not artificial savings. Post-event optional insights: what could prevent a similar purchase next time, no shame.
6. DAILY FLOW B — LOW STOCK & SHOPPING
Low stock is NOT expiry. Only remind about household staples explicitly marked staple, minimum threshold or last-confirmed needs, never infer item gone purely from expected meal consumption. Home: 'Rice might be running low — confirm before adding' if last confirmed and expected use implies possibility. Daily routine: add item to list by voice/text, typed checkbox or photo of handwritten grocery list; Gemini extracts item/quantity candidates; user edits/confirms. Store photo/list source and privacy.
While shopping: take photo of pack/product shelf, enter name, barcode optional; compare with last-confirmed kitchen stock, current household list, meal plans, price/pack size as given by user or authorized catalog. Results 'Confirmed: 1kg rice last checked yesterday' vs 'Uncertain: milk was last checked 10 days ago', do not claim possession when stale. Show 'Buy', 'Maybe skip', 'Need to verify', 'Add to list' with reasons. Offer comparison of smaller packet vs bundle only if comparable unit price and needed amount are grounded; discount can cause overbuying.
After shopping: upload photo of receipt, text message or import AUTHORIZED grocery orders → extraction candidates → confirm actually delivered quantity (substitution/refund handling) → stock update. Purchases do not imply food was still at home or edible. Need easy correction of consumed items and occasional 'review shelf' photos rather than daily full fridge rescans.
7. DAILY FLOW C — CONVERSATIONAL COOKING + IMAGE/VIDEO HELP
A dedicated Ask EcoLoop screen with example chips 'What can I cook in 20 minutes?', 'Use my tomatoes', '2 people won't eat tonight', 'What should I buy?', 'Can I replace this ingredient?'. User can attach ONE photo of ingredient/pack, handwritten recipe/menu, kitchen shelf or fridge. Gemini sees only what uploaded; all inferred items are candidate until confirmed. Use explicit preferences, number of diners, cook time and confirmed stock; show meal options with explainability and missing ingredients. Deterministic quantity calculator rather than free-form nutrition/serving math in model. Agent may propose save meal plan, add missing items to shared list, mark ingredients used; user explicitly approves changes.
Video-assisted candidate P1: upload short clip if multimodal API, privacy/size/runtime and latency workable; use images first because cheaper/faster and accessible; do not do continuous kitchen surveillance or infer spoilage from video. Voice note/streaming conversation optional if reliable. Chat must be actionable with cards/buttons instead of forcing user to type commands for normal stock edit. Simple, opt-in health guidance: support regular meals, variety, user preference for more home cooking and portion planning; cannot infer nutrients consumed, medical conditions or 'healthy/unhealthy person' from order history. Avoid calorie ranking/shaming or medical advice. Basic nutritional info only if sourced and contextual, not personalized diagnosis.
8. DAILY FLOW D — CHANGING PLANS / SHARED MEAL ATTENDANCE
Home meal card: next breakfast/lunch/dinner approximate time if opted in, expected number eating (specific members opt-in if shared). User types 'two people eating out' or member clicks Eating home / Not home / Unsure; system updates count only after permissioned event, not individual restaurant location. Cook sees old vs new count, current planned meal and confirmed ingredients. Gemini interprets intent and offers 1-2 adjusted plans, calculator recomputes ingredients; member/owner approves; if already prepared mark leftovers rather than false reversal. Later feedback one-tap Eaten / Stored / Discarded / Not sure; not mandatory per-person consumption. Family invite links optional and permissioned; owner should be able to enter household number manually without inviting anyone.
9. CONNECTED COMMERCE FLOW — SOURCE-SPECIFIC PERMISSIONS
Connection is optional from Profile / Connections or shopping flow; it is NOT compulsory onboarding. UI shows provider, exact accessible data scope and privacy: 'Read recent grocery orders', 'Read food delivery orders', 'Use frequent items' where documented and consented; user explicitly authenticates through provider OAuth when supported and can revoke. Never ask user to hand over password or scrape private app.
Swiggy developer docs 2026 show Instamart MCP `get_orders`, `get_order_details`, `your_go_to_items`, plus Food MCP `get_food_orders`, `get_food_order_details`; published client integration uses OAuth2.1 PKCE and production HTTPS redirect allowlisting. End-to-end live EcoLoop authorization not verified; local developer testing supported by provider docs but do not claim connected. Food ordering data is orders, not confirmed calories or meals consumed. Grocery purchases do not equal current fridge stock. Only show order frequency within actually accessible historical window, avoid household surveillance, and let user choose [order count/timing patterns only] vs [specific order items retained]. Analysis suggestions: order out often during weekdays (descriptive, avoid shame); consider adjusting meal plan or buying smaller groceries if verified as useful. Models should not label 'unhealthy' or diagnose based on order logs.
Zomato public developer POS integration docs are for restaurant software; no verified consumer order-history API permissions for arbitrary personal users from these sources. Label Zomato Connect 'Not supported / coming later' and offer manual screenshot / receipt import with source approval. Other platforms also simulation until legal scope verified. No merchant order/autocheckout in MVP.
First-party sources https://mcp.swiggy.com/builders/docs/reference/instamart/ ; https://mcp.swiggy.com/builders/docs/reference/food/ ; https://mcp.swiggy.com/builders/docs/start/authenticate/ ; https://www.zomato.com/developer/integration/docs/api-documentation/order-management/ .
10. NOTIFICATION & REMINDER STRATEGY
Notification types: labeled date approaching, stale stock confirm, low staple, upcoming meal confirmation, optional weekly kitchen review. Defaults: in-app attention center; user chooses which alerts and quiet hours. 'Expires tomorrow' only from verified label expiry/use-by; best-before and unverified observations visibly different. User can snooze, mark resolved, mute item/category; notification dedupe and cancellation when consumed/discarded. Prioritize 1 useful notification rather than a flood. Tech: Firestore event+Cloud Tasks/Scheduler event and Firebase Cloud Messaging web where supported; FCM Push API requires HTTPS and browser support. On unsupported browsers, in-app reminders still work. Need user consent, service worker and device/browser compatibility tests; no push guarantee on all iOS devices. Sources https://firebase.google.com/docs/cloud-messaging/web/get-started and https://firebase.google.com/docs/web/pwa .
11. PRODUCT DATA MODEL (CONCEPTUAL, NOT ACTUAL STORAGE)
User {id, name, chosen_language, notifications_opt_in, meal_time_preferences?, general_goals?, consent_records}. Household {id, name, type SOLO|SHARED, admin_id, members, invite_token_expiry, sharing_policy}. Membership {user_id, household_id, role, scope, accepted_at}. InventoryObservation {household_id, item_id, name, quantity, unit, purchase_source, observed_at, confirmed_at, confirmed_by, expiration_date?, label_type USE_BY|EXPIRY|BEST_BEFORE|USER_TARGET|UNKNOWN, storage_assertion?, status confirmed|candidate|stale|disputed}. MealPlan {id,date,meal_time,headcount,member_responses (private minimal), status, approved_by}. ShoppingItem {item, qty, source photo/list/cart, status desired|purchased|delivered_confirmed|declined, owner}. CommerceConnection {user_id,provider,scopes,oauth_state,enabled,retention,no shared access by default}. OrderObservation {user_id, source, order_type FOOD_DELIVERY|GROCERY, order_time, items user-approved, partial/refund status, consent}; NOT authoritative consumption/stock. Reminder {type, evidence_source, due_at, muted, resolved, assigned_to}. Outcome {item, eaten|shared_at_home|stored|discarded|unknown, weight_measured?, method, time, actor, source, edible_flag_user_reported}; sustainability impact only independently justified. User actions: confirm/modify/revoke always accessible.
12. SCREEN INVENTORY FOR CODING (CONCEPTUAL ROUTES)
ONBOARD: S01 `/` landing; S02 `/sign-in`; S03 `/setup/type`; S04 `/setup/create-family` OR `/setup/join-family`; S05 `/setup/preferences` skippable; S06 `/setup/add-food`; S07 `/setup/confirm-food`; S08 `/setup/first-result`.
CORE: S09 `/home` Today and priorities; S10 `/kitchen` stocks/use-soon filters and confirm; S11 `/kitchen/:id` item history/quantity/date type/reminders; S12 `/ask` conversational cook/meal with image/voice and actionable response; S13 `/plans` meal headcount and changes; S14 `/shopping` list/check-before-buy/receipt capture; S15 `/capture/review` shared sheet for parsed candidates (not one route for each scan); S16 `/attention` reminders grouped with action cards; S17 `/outcome` simple used/shared/stored/discarded sheet (not full page); S18 `/household` members/invites; S19 `/settings/connections` opt-in Swiggy, manual import; S20 `/progress` actual logged outcomes and spending when grounded.
MVP PAGE CONSOLIDATION: 4 top-level pages Home/Kitchen/Ask/Shopping + onboarding + small sheets/dialogs for family, reminders, item detail, capture and outcome; Plans accessible as prominent Home action, not necessarily a fifth permanent nav. S19/20 optional build. Many S IDs describe states, not 20 full independent development projects.
13. PRIORITIZATION TO AVOID HACKATHON SCOPE EXPLOSION
P0 one credible working end-to-end: solo/family-choice account (family invite only if easy), Home, add/confirm 3 items from photo/list/receipt, conversational changed meal plan, 1-2 meal suggestions, last-confirmed-use-soon action card, explicit mock shopping draft, simple outcome update and persisted Firestore state. Build first-value even without integrations.
P0.5 if remaining time: create/join household with one member, member confirms attendance, simple shopping list photo extraction, low stock manual flag and gentle reminder settings.
P1: actual Swiggy order history via OAuth only if provider permitted and authentication working; patterns and privacy scopes; web push FCM where supported; persistent family permissions and richer shopping assistance; dated item detail UX.
P2: video, detailed lifestyle analytics, automatic restock estimation, community safe surplus donation/operator integration, carbon/water modeling, home compost municipal lookup, full PWA offline, real checkout, personalized diet tracking.
Hard reject hackathon: no Play/App Store; no food-safe certifications from photos; no 'expired item donate'; no health diagnoses or calorie profiling from orders; no full location/child surveillance; no false measurable sustainability savings; no autonomous payment; no integration claim without authenticated test. Model helps interpretation; code handles amounts/roles.
14. GAPS, QUESTIONS AND DESIGN TESTS
Question A: Household access: Is family invitation + meal attendance essential to demonstrate benefit? The initial solo-only flow may prove feature usefulness without privacy complexity. Default recommend create/join option in UX and demo with seeded roles, real invites later if time.
Question B: Does the user want to inspect `stock` vs simply last purchases? Tracking constantly becomes work. Test first-use suggestion and weekly 30-second kitchen refresh using user uploaded list/photo vs dynamic planning with only last confirmed relevant items. No silent decreases.
Question C: What exactly does commerce connect yield? Official Swiggy MCP has order history and go-to items; ensure authenticated history horizon/scopes and user agreement. Do not infer actual consumption or nutrition.
Question D: Label policy, special cases and food handling require date type & storage uncertainty. FSSAI 2025 compendium distinguishes expiry/use-by and optional best-before labeling: https://stg-old.fssai.gov.in/upload/uploadfiles/files/Comp_Labelling%20Display_Version%20VIII_09_09_2025.pdf ; interpret only current authoritative version and ask user if uncertain.
Question E: Do we actually need a daily use-soon push, or just home action card? A/B test notification permission opt-in and whether user acts; no default notification spam.
Question F: User wants general healthy lifestyle support; minimum lovable intervention: optional schedule nudges, variety goals and home-cooked meal tracking with explicit consent, not medical nutrition diagnosis.
Question G: Individual consumption per member? Strong recommend OUT of MVP, aggregate household food event and personal voluntary preference enough.
Evaluation: onboarding time to first useful decision target under two minutes (unmeasured); steps to confirm 5 items and correct 1 error; user action rate on use-soon; duplicate purchase correction rate; cook plan adaptation; log burden and push opt-out; compare ordinary Gemini/manual list vs connected app. Actual prevented food waste requires measured counterfactual, not inferred from an alert.

CONSUMER UX ADDENDUM — AGENT MEMORY, ADAPTIVE CHAT UI AND SUSTAINABILITY (15 OCT 2026)
Consumer product design decision: Google Gemini Enterprise Agent Platform + ADK + Agent Platform Sessions + Memory Bank are CORE, with per-user consent and scoped persistence. Firestore is authoritative for confirmed quantity, purchase/meal actions, dates, reminders and outcome events; Memory Bank only stores consented reusable preferences, recurring meal timing and cooking habits; Sessions hold active conversation context. No child or household member's private commerce record placed in shared Memory Bank. Provide "What EcoLoop remembers" view, correction and deletion; implement gated memory updates after user confirmation, not arbitrary raw chat saves. Protect against prompt injection/memory poisoning.
Generative UI: EcoLoop's Next.js shell/layout/navigation remains deterministic. Inside chat, Gemini+ADK should produce structured response types and interactive typed cards (recipe options, adjustable serving counts, ingredient used/needs-confirmation lists, shopping comparisons, reminder resolution and approval sheets). User actions go through FastAPI typed permissioned endpoints; never run LLM-generated JS/HTML. Begin with 4-5 fixed components, then investigate Google-led A2UI v0.9.1 @a2ui/react renderer/custom component catalog if supported in build. A2UI currently early-stage preview; optional for MVP. Show visually meaningful "conversation → card → approval → Firestore outcome" rather than prose only.
Dashboard: Today has (1) next best action, (2) meal plan and confirmed inventory, (3) use-soon/low-stock checks, (4) concise sustainability progress. P0 sustainability signals split "Actions recorded" [items marked used, dates reviewed, meal plan adjustments, decisions on potential duplicate purchases] from "Outcomes actually logged" [measured edible discarded grams/kg, status of stored/shared items, shopping expenditure only if price entered]. No "kg saved", water, CO2e or money saved as actual unless a defensible counterfactual and measurement support it. Example display: 3 items need a check, 2 meals planned using confirmed ingredients, food waste log incomplete — review when convenient. If no data show meaningful onboarding prompt instead of fake '0 kg waste'. P1 4-8 weeks trends, with complete-data denominators; P2 expansion modules other independently metered resources (water litres, energy kWh, materials actually reused), each source/period/provenance/confidence. A composite "eco score" across kg, kWh and litres is deceptive without justified methodology.
One concrete conversational experience: user says "Two people are out tonight" → Gemini parses meal-change event; ADK reads confirmed meal plan, pantry facts, personal preference Memory Bank; backend calculates portions → Next.js displays an editable meal card with previous/new portions, missing items and buttons "Use this plan", "Add missing ingredients", "Keep original", "Need to check fridge". After user confirmation record approval and time. Follow up optionally eaten/stored/discarded, never infer saved kg.
P0 build gate: real Gemini model call, ADK tool selection, managed Sessions + at least one explicit opt-in Memory Bank preference surviving across two distinct sessions, and one dynamic typed chat card with working approval. Verify GCP project IAM/billing/region/Memory Bank. Agent Platform Runtime strongly preferred for ADK if available, Cloud Run backend retains authority. Eval memory scope leakage, irrelevant/stale memory, and generated UI forbidden action/tool injection.
