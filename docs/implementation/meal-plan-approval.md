# Meal proposal approval slice — 17 October 2026

This local backend slice adds `POST /api/v1/assistant/proposals/{proposal_id}/meal-actions` in `backend/app/api/v1/endpoints/meal_plans.py`. It reads the server-persisted assistant proposal receipt and applies APPROVE, EDIT, or DISMISS transactionally. Proposal ownership, household, pending status, expiry, and version are checked; the authenticated active membership is rechecked in the transaction. Retries are actor-scoped and payload-bound.

Approving a `MealSuggestion` creates a version-1 `meal_plans/{proposal_id}` record. Numeric, non-uncertain quantities with recognized explicit units are stored as `ASSISTANT_ESTIMATE`, never measured facts; other quantities retain unknown provenance. An explicit `EDIT` that changes servings scales those assistant estimates only when preparation is `NOT_STARTED`. A `PortionAdjustment` requires exactly one server-provided `source_refs` plan ID and matching proposal/plan base versions. Its explicit approval or edit ignores model-provided `card.changes` and scales only quantities already saved on the plan with `MEASURED` or `ASSISTANT_ESTIMATE` provenance, finite numeric amounts, certain values, and recognized units; edits scale only before preparation. Unknown, incompatible, uncertain, malformed, and unrecognized-unit quantities are preserved. Partly prepared, already cooked, and unknown-stage plans keep all ingredient quantities and receive stage-specific guidance; nothing implies uncooking or consumption. `proposed_servings` is accepted only for `EDIT`. No Kitchen item or stock record is read or modified.

## Integration seam and limitations

`backend/app/api/v1/router.py` includes this router, and the Ask renderer/allowlisted frontend transport call the meal-action endpoint. Existing `PortionAdjustmentCard` has no dedicated plan ID or persisted measurement provenance. This handler uses its single server-authored `source_refs` entry as the plan ID and fails closed if that shape is absent or ambiguous. The ADK context tool now reads bounded saved plans, and the proposal producer must cite a returned plan ID/version before this path can succeed. Existing general BuyCheck proposal actions remain separate. Browser acceptance and a real model-generated PortionAdjustment tied to a saved plan remain unverified.

No cloud/provider calls or unit tests were run. Python compile and module-import checks, plus a bounded local deterministic-scaling smoke check, passed.
