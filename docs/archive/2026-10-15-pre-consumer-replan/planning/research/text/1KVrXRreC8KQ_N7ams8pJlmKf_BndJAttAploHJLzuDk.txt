﻿ECOLOOP AI — WEB-FIRST PRODUCT REQUIREMENTS DOCUMENT v0.2
15 October 2026. Provisional scope; requirements represent a comparison prototype, not a decision that market need or product has been validated. One responsive web app, optional installable PWA. All AI/model infrastructure Google-owned.


VISION, TARGET, NON-GOALS
Core proposition: low-friction real-world resource decisions, visible explanations, controlled actions, measured outcomes; food-first while architecture can extend to recovery, circularity, water, cooling and repair. Persona-specific surfaces: household shared food coordinator (shopping, cooking, eating), kitchen manager and chef, food donor+registered NGO coordinator+consenting recipient, apartment RWA+waste collector+authorized compost operator. Different permissions/safety rules. No generic super-app MVP.
P0 comparison slice: one case per A/B/C with identical common interface/components and 12–20 gold cases per lane. P0 no external purchases, no auto-donations and no inferred pathogen safety. P1 authorized Swiggy MCP, real NGO integration, Maps routing, operator audit; P2 apartment wet-waste outcome tracking, cooling and water. No Play Store or App Store.


USER ROLES AND TENANCY
TenantType HOUSEHOLD; roles owner, adult member, cook (limited access), diner (schedule-only). TenantType KITCHEN; roles manager, chef, headcount coordinator, auditor, diet/medical authority where appropriate. TenantType RECOVERY; roles food donor, registered qualified NGO coordinator, driver, verified receiving organization, auditor. TenantType ORGANICS research: resident, RWA officer, collection worker, permitted processor and verifier. Single user can have multiple tenant memberships but no cross-tenant data except an explicitly approved transfer with records. Anonymous/demo mode uses seeded synthetic records and clearly DEMO signage; authenticated real storage only after consent.


WEB INFORMATION ARCHITECTURE
Landing: current problem, affected users, 'Try safe demo' and explicit simulated status. Auth invite/roles. Demo chooser: Household A; Institutional kitchen B; Food recovery C. Context intake: photo/receipt/text/audio notes where permissioned. Extracted facts review: edit source/date/quantity; no silent writes. Decision: top 1–2 options, evidence, rationale, uncertainty, impact status NOT MEASURED. Review/approve: act only inside simulated adapters; authorized real action only future. Outcome log: measured edible discard, weighed kitchen categories, qualified NGO received/accepted kg and actual consumed where available; no invented CO2e. Partner portal: offers, capacities, approvals, material eligibility, rejects, custody events; separate future wet-waste portal. Evaluation admin: gold cases, trajectories, correction metrics, baseline comparison and method. Settings: membership, permissions, personal context view/export/delete, notification opt-in.


P0 FUNCTIONAL REQUIREMENTS
PRD-001 URL delivers secure functional responsive app on desktop/tablet/mobile, keyboard and screen-reader-friendly.
PRD-002 Explicit consent roles; don't collect others' schedules covertly. Demo mode entirely synthetic.
PRD-003 P0 structured candidate intake via Gemini; quote evidence and timestamp, require human correction; no food-safety certification.
PRD-004 Date/versioned Firestore facts and provenance; separation verified vs inferred/disputed/stale.
PRD-005 A: changing dinner attendance, confirm inventory and deterministic quantity adjustment, show use-first and draft cart.
PRD-006 B: record planned vs actual meals, late roster events and cutoff, kitchen chef approve; ensure menu nutrition/safety constraints.
PRD-007 C: offer, handling evidence, eligibility NEEDS HUMAN REVIEW, partner confirmation, safe custody record; never automatic recipient placement.
PRD-008 Shared explicit action-preview, human approval and auditable result state; end-to-end test verifies forbidden calls blocked.
PRD-009 Physical metric capture distinguishes edible and inedible waste; separate consumed, donated, collected, processed, discarded, as appropriate.
PRD-010 Baselines: rules+Sheets/Forms, ordinary Gemini and available incumbent workflows with comparable inputs.
PRD-011 Clear unknowns/uncertainty and no fake impact numbers; dated original sources in UI where shown.
PRD-012 Performance/cost tracing and error/evaluation result export; no hard latency SLA until test.
PRD-013 Responsive navigation/role-based dashboards, privacy settings and data retention policy confirmation.
PRD-014 Incentives optional opt-in and evidence-based; do not reward buying more/donating unsafe food/generating wet waste.
PRD-015 MCP provider discovery does not imply permitted API, user authentication or checkout.


PWA TRADE-OFF & EXPERIENCE POLICY
Decision web-first: one Firebase Hosting URL, browser compatibility, test with Chrome and Safari mobile/desktop, share instantly and deploy continuous revisions. No app store provisioning. Use React TypeScript (chosen for web focus) + Vite; Flutter Web is a Google-supported alternative but introduces heavier runtime and less natural browser DOM semantics for content-heavy portals. Use accessible component library with appropriate license; no external AI services.
PWA P1: manifest, icons, install prompt only when supported; service worker with versioned static assets, offline read-only forms/drafts only if fully scoped and encrypted/limited; purge sensitive caches on logout, avoid service worker stale version serving wrong food-safety policy. Notifications P2 consent, opt-in and no urgency pressure. Avoid device camera or mic being mandatory: file upload and plain typed input fallback. Content updates and online trust checks win over offline promise.
PWA installability varies across browsers and devices; do not claim background sync/push identical support on all. Tests: desktop browser, Android Chrome, iOS Safari and slow network. Link data deletion/consent in settings; don't store restaurant credentials in browser localStorage.


KEY USER ACCEPTANCE CRITERIA
An authenticated or clearly labeled demo user can complete each P0 journey with no real external payment/donation; machine-extracted field requires confirmation; each action shows actor, data source and uncertainty; false expiry/safety claim blocked; data from tenant A never appears in tenant B; a deliberately malicious receipt cannot call purchase tool; user can see what was saved and edit/delete according to retention policy. Accessibility AA-oriented checks (keyboard, contrast, labels, screen reader) and mobile touch targets. Verify rendering 360px–1440px. Record demo metrics only as synthetic, physical savings NOT MEASURED. Future real donor and partner records require written consent.


PRODUCT DECISION TRADEOFFS
Why roles vs giant single chat: different people control authority and data; prevents false autonomy. Why source-aware temporal data vs AI memory: food stock and safety change. Why structured tools vs pure prompt: testability, determinism and access control. Why mock external calls: rights unknown. Why zero autonomous donations: eligibility/safety/legal. Why avoid paid incentives at first: financial deals and rebound evidence unproven. Why three skeleton modules: scientifically fair choice before finalist, shared infrastructure limits cost; NOT three production apps. Why organic waste separate: different material category and operator rules. Primary adoption barrier: work to keep pantry/meal counts up to date. All new UX must reduce not increase burden.


COMPETITION AND NEXT TESTS
NoWaste, Samsung Food, Panasonic KitchenPocket and shared communication already address inventory/recipes/household advice. Swiggy MCP supports commerce in approved settings; getting a cart done is not original. Winnow/Leanpath and non-AI kitchen signage/portions already prevent some measured food waste. IFSA/NGOs/Goodr and volunteer coordination already provide recovery; logistics dominate. Saahas/Hasiru Dala already support organic collection/compost. Before selecting A, B, C run same gold cases on Sheets+rules, ordinary Gemini, accessible incumbent workflow and EcoLoop; judge correct task, user minutes, user errors, cost and severe policy failures. No physical impact claims from scenarios.
